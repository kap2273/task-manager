# RETRO — Week 5: Plan, Decompose, and Supervise

## 1. Plan Mode value

The clearest case was **Session 1** in PLAN_LOG.md. My prompt asked for priority on `POST /api/tasks`, and Claude's plan stopped to flag that CLAUDE.md says "Do not change the signatures of ... `create_task`". Instead of picking Claude's suggested option, I amended the plan with three conditions. First, only an optional trailing `priority: int = 3`, so every existing caller in routes/api.py and tests/test_tasks.py kept working. Second, the 1–5 check had to go in a private `_validate_priority` helper in services/tasks.py, not the route. Third, bools had to be rejected. The third condition would have needed a revert later. In Python `isinstance(True, int)` is `True`, so a plain integer range check would have accepted `{"priority": true}` and saved it as priority 1, and neither my original prompt nor Claude's question mentioned bools. Because of the amendment, `_validate_priority` checks `isinstance(priority, bool)` first, and `test_create_task_priority_non_int_raises_validation_error` covers `True`. **Session 3** shows the same benefit on a smaller scale: the plan would have rejected `"-1"` with "must be an integer". My amendment made it return "must be between 1 and 5", which `test_list_tasks_priority_out_of_range_raises_validation_error` now locks in.

## 2. Plan Mode limits

In **Session 3** I approved an amended plan that said exactly which code would be written: `digits = priority[1:] if priority.startswith("-") else priority` in services/tasks.py, and a one-line `from services.tasks import ...` in routes/api.py. After approval, Claude ran `python -m ruff check` because CLAUDE.md says "Before finishing any task: ... `ruff check` is clean." Ruff flagged both lines, and Claude rewrote them to `priority.removeprefix("-")` and a 7-line import block without asking me. It only told me afterwards. The behavior was the same, but the code was not what I approved. This shows where Plan Mode stops being reliable. Approval controls what Claude *intends* to do, but once execution starts, any check Claude runs (ruff, pytest) and any rule in CLAUDE.md can override the plan, and nothing stops it to ask first. Plan Mode is also only as reliable as remembering to turn it on: in **Session 2** and my first attempt at **Session 4**, `/clear` had reset the mode. Claude still wrote "Here's the plan, I haven't changed anything yet" because my prompt asked, but the plan was just chat text. Typing "yes" let it edit files with no approval step and no saved plan file. In the transcript the two look almost the same, and that is the risk.

## 3. Subagent value

The most important boundary was between **SA-2 (services/users.py) and SA-3 (routes/api.py)**. The SA-3 constraint ("Only edit routes/api.py ... no validation or if-statements on the value") kept the allowed-values check in exactly one place, `update_notification_pref` in services/users.py, which SA-4 could then test directly with `"push"`, `""`, `"EMAIL"`, `None` and `5`. Task 1 shows what happens without that boundary. In a single session Claude mixed the layers: in **Session 1** it put `data.get("priority", DEFAULT_PRIORITY)` in the route, so the route has to know a service default. Decomposing also showed me a gap that a single session would have hidden. Because SA-2's hand-off took an already-extracted `pref` value, nobody owned "is the request body a JSON object?". `PATCH /api/users/1/notifications` with body `["sms"]` still crashes with a 500, and SA-4's 20 tests didn't catch it because its prompt only listed bad values. In one session Claude would probably have patched the body handling quietly while writing the route, and it would have written tests for its own implementation rather than for the spec. The separate SA-4, given only the files and the spec, is what showed that the tests only cover what the prompt lists.

## 4. Gap analysis

The rule I would most want enforced mechanically is the **Output/Constraint field of each subagent: "Only edit routes/api.py. Do not edit anything in services/, utils/, or tests/"** (SA-3), and its equivalents for SA-1, SA-2 and SA-4. It held this time, but only because Claude chose to follow it. SA-2 wrote to services/users.py with a shell heredoc (`cat >> services/users.py <<'EOF'`), and SA-3 rewrote all of routes/api.py with a Python script ("+57 −39"), so neither went through Claude's normal Edit tool. That means a hook that only watched Edit/Write would not have seen either write. **Hook spec:** after every Edit, Write *or* Bash tool call, a hook runs `git diff --name-only` and blocks Claude, showing the offending path, if any changed file is not in the current subagent's allowed Output list (for SA-3, only `routes/api.py`).
